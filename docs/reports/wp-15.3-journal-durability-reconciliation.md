# Work Package 15.3 — Framed Recovery Journal, Durability and Conservative Crash-State Reconciliation Report

## 1. Executive Summary

Work Package 15.3 implements durable transaction recording and conservative, read-only crash-state reconciliation for Root's Guardian subsystem. Prior to this work package, the Guardian journal utilized line-delimited JSON Lines (v0 JSONL) without framing headers, record integrity checksums, explicit durability guarantees, or torn-write detection.

This work package introduces:
1. **Framed Journal Format (Version 1)**: A 16-byte binary header (`MAGIC`, `VERSION`, `FLAGS`, `CRC32`, `LENGTH`) preceding each JSON record payload, capped at a strict 64 KiB payload limit, and bounded by newline delimiters.
2. **Durability and Concurrency Coordination**: Explicit filesystem synchronization (`sync_data` and parent directory synchronization) coupled with cross-process advisory file locking via `root_platform::AdvisoryLock` to guarantee atomic record append boundaries.
3. **Legacy Compatibility**: Transparent read-only detection of legacy v0 JSONL journals with explicit refusal to append framed records into unmigrated legacy logs.
4. **Read-Only Crash-State Reconciler**: A strictly non-mutating inspection engine (`JournalReconciler`) that evaluates journal evidence against filesystem metadata (without following symlinks) to conservatively classify transactions into deterministic categories (`KnownNotPerformed`, `KnownPerformed`, `Uncertain`, `JournalInvalid`, `RecoveryRequired`).
5. **Deterministic Fault-Injection Suite**: Twenty-eight synthetic test scenarios in `guardian_journal_reconciliation_tests.rs`, validating framing round-trips, trailing torn-write detection, bit corruption, out-of-order state transitions, crash points, and filesystem immutability.

All 332 tests across the Root workspace compile and pass cleanly, with zero compiler or clippy warnings, zero emojis, and zero alterations to production read-only boundaries.

## 2. Work Package Scope and Context

Root remains an unprivileged, local-first Linux utility operating strictly in read-only inspection mode. In Work Packages 15.1 and 15.2, directory descriptor abstractions and descriptor-pinned validation pipelines were established to mitigate time-of-check to time-of-use (TOCTOU) path substitution attacks.

Work Package 15.3 addresses the storage layer beneath Guardian transactions. In the event of system power failure, kernel crash, process termination, or storage disconnection during a mutation:
- Journal records could be partially written or truncated.
- Filesystem changes (relocations) could precede or follow journal updates.
- Future recovery mechanisms could misinterpret incomplete logs.

WP-15.3 addresses these failure modes by providing verifiable durability, framing integrity, and conservative state reconciliation without enabling automatic recovery or production filesystem mutation.

## 3. Framed Journal Format Specification

### 3.1 Binary Header Layout

Each framed journal record begins with a fixed 16-byte binary header encoded in big-endian byte order:

| Byte Offset | Field Name | Type | Description |
|---|---|---|---|
| 0..4 | `MAGIC` | `[u8; 4]` | Fixed ASCII magic bytes `b"RTJR"` (`0x52, 0x54, 0x4A, 0x52`). |
| 4..6 | `VERSION` | `u16` | Record format version. Set to `1`. |
| 6..8 | `FLAGS` | `u16` | Header flags. Reserved for future extensions; must be `0`. |
| 8..12 | `CRC32` | `u32` | IEEE 802.3 CRC-32 checksum computed over the record payload bytes. |
| 12..16 | `LENGTH` | `u32` | Exact byte length of the UTF-8 JSON record payload. Maximum: 65,536 bytes. |

The binary header is immediately followed by:
- `PAYLOAD`: Exactly `LENGTH` bytes containing valid UTF-8 JSON representing a `JournalRecord`.
- `DELIMITER`: A trailing newline byte (`\n` or `\r\n`).

### 3.2 Integrity Checking and CRC-32 Implementation

Payload integrity is validated against standard IEEE 802.3 CRC-32 (polynomial `0xEDB8_8320` reversed). The lookup table is computed at compile time (`const [u32; 256]`), eliminating external crate dependencies. The implementation is verified against the standard FIPS/NIST test vector `b"123456789"` (`0xCBF4_3926`).

### 3.3 Defensive Bounds

To guard against malicious or corrupt headers triggering memory exhaustion, payload length is strictly constrained:
- Maximum permitted payload length: `65,536` bytes (64 KiB).
- Any header declaring `LENGTH > 65,536` is rejected as `JournalCorruption::OversizedPayload` without allocating buffer memory.

### 3.4 Torn-Write and Corruption Detection

The journal parser distinguishes between non-fatal trailing torn writes and unrecoverable internal corruptions:
- **Torn Write at EOF**: An incomplete header (< 16 bytes) or incomplete payload (< declared `LENGTH` bytes) occurring at the end of the file is classified as a trailing torn write. Prior valid records in the journal are fully preserved and readable.
- **Unrecoverable Corruption**: Invalid magic bytes, unsupported format versions, oversized declared payload, CRC-32 checksum mismatches, or malformed JSON payloads in non-terminal or terminal records are classified as unrecoverable defects requiring operator intervention.

### 3.5 Legacy JSONL Compatibility

Legacy journals (unframed line-delimited JSON Lines beginning with ASCII `{`) are automatically detected:
- **Read-Only Access**: `scan_records()` parses valid legacy records.
- **Mixed-Write Prevention**: `append()` explicitly rejects appending framed v1 records to a detected legacy journal with an explicit error (`"Legacy v0 JSONL journal detected; appending framed records without explicit migration is prohibited"`).

## 4. Durability Model and Write-Ordering Invariants

### 4.1 Write Ordering

Guardian enforces a strict ordering protocol during transactional operations:
1. **Pre-mutation Intent**: Record `TransactionState::Prepared` in the recovery journal.
2. **Journal Durability**: Flush and synchronize journal data to physical non-volatile storage (`sync_data()`).
3. **Directory Durability**: Synchronize the parent directory file descriptor (`sync_all()`) to persist the journal directory entry.
4. **Filesystem Mutation**: Execute atomic object relocation (`renameat2` with `RENAME_NOREPLACE` or descriptor-relative relocation).
5. **Post-mutation Record**: Record `TransactionState::Quarantined` in the recovery journal.
6. **Integrity Verification**: Verify quarantined object hash and unlink status.
7. **Terminal Record**: Record `TransactionState::Verified`.

### 4.2 Synchronization Semantics

Every journal append executes:
- `file.write_all(&framed_bytes)`: Writes the framed buffer atomically.
- `file.flush()`: Clears user-space I/O buffers.
- `file.sync_data()`: Issues `fdatasync()` on Linux to force metadata and payload blocks to disk.
- `pfile.sync_all()`: Issues `fsync()` on the parent directory when accessible.

### 4.3 Concurrency Control

To prevent concurrent processes or threads from interleaving record bytes or tearing writes, `RecoveryJournal::append()` acquires an advisory lock (`root_platform::AdvisoryLock::acquire`) on a sidecar lock file (`<journal>.lock`). The lock is released via RAII when the guard drops.

## 5. Crash-State Reconciliation Architecture

The crash-state reconciler (`JournalReconciler`) is a deterministic, strictly read-only analysis engine. It inspects journal history and probes current filesystem evidence to establish the exact status of interrupted transactions.

### 5.1 Operating Principles
- **Strictly Read-Only**: Reconciliation never alters, moves, restores, deletes, or truncates any file or journal record.
- **Conservative Inference**: In the presence of ambiguous or contradictory evidence, the engine classifies the transaction as `Uncertain` or `RecoveryRequired`—it never guesses or executes automatic rollbacks.
- **Symlink Safety**: File probes utilize `symlink_metadata()` without traversing symbolic links, preventing scope escape or target manipulation.

### 5.2 Crash-Recovery Matrix

| Scenario | Journal Tail State | Source Path State | Destination Path State | Identity Match | Reconciled Outcome | Meaning |
|---|---|---|---|---|---|---|
| 1 | `Prepared` | Exists | Absent | Source matches pre-intent identity | `KnownNotPerformed` | Interrupted before relocation; source intact; no action needed. |
| 2 | `Prepared` | Absent | Exists | Destination matches pre-intent identity | `KnownPerformed` | Relocation succeeded before commit record appended. |
| 3 | `Prepared` | Exists | Exists | Ambiguous | `Uncertain` | Collision or partial state; operator review required. |
| 4 | `Prepared` | Absent | Absent | N/A | `Uncertain` | Resource missing from both locations. |
| 5 | `Quarantined` / `Verified` | Absent | Exists | Destination matches expected | `KnownPerformed` | Transaction completed successfully. |
| 6 | `Quarantined` / `Verified` | Exists | Absent | Source matches expected | `RecoveryRequired` | Committed in journal but resource still at source. |
| 7 | `Quarantined` / `Verified` | Exists | Exists | Destination matches; source is new object | `KnownPerformed` | Quarantined successfully; source recreated by user or build tool. |
| 8 | `Quarantined` / `Verified` | Absent | Absent | N/A | `RecoveryRequired` | Quarantined object missing from filesystem. |
| 9 | Torn write at EOF | Any | Any | N/A | Evaluates prior valid records; flags torn write | Non-fatal torn write at journal end. |
| 10 | Corrupted record (bad CRC / magic) | Any | Any | N/A | `JournalInvalid` | Corrupted journal record; requires operator investigation. |
| 11 | Unexpected identity | Any | Exists | Destination identity mismatch | `RecoveryRequired` / `Uncertain` | Destination exists but contains unexpected object. |

## 9. Verified Guarantees and Invariants

1. **Framing Integrity**: Every v1 journal record is protected by a 16-byte binary header with an IEEE 802.3 CRC-32 checksum. Single-bit errors or altered payloads are reliably caught.
2. **Defensive Allocation**: Payload lengths are bounded at 64 KiB, preventing crafted headers from causing memory denial-of-service.
3. **Torn-Write Resilience**: Interrupted appends at EOF do not prevent the recovery and inspection of prior valid records.
4. **Mixed-Version Prevention**: Framed records are never silently mixed into legacy JSONL logs.
5. **Durability Ordering**: Physical storage synchronization (`sync_data()`) occurs before subsequent mutation steps are initiated.
6. **Concurrent Writer Isolation**: Process-level advisory locks prevent interleaved appends across concurrent executions.
7. **Zero Filesystem Mutation in Reconciler**: Reconciliation is strictly read-only inspection; it never alters, restores, moves, or deletes resources or journal files.
8. **Conservative Crash Classification**: Incomplete or ambiguous filesystem evidence produces `Uncertain` or `RecoveryRequired` classifications rather than automated rollbacks.

---

## 10. Explicit Limitations and Non-Goals

1. **No Automatic Recovery**: WP-15.3 deliberately does not implement automatic rollback, journal truncation, or file restoration. Reconciliation is an advisory inspection diagnostic only.
2. **No Production Mutation**: Production CLI and GUI interfaces remain strictly read-only.
3. **Cross-Platform Storage Durability**: While the framed format and reconciler are portable across Unix and Windows, descriptor-pinned atomic relocation (`renameat2`) and Linux parent-directory sync semantics remain specific to Linux platforms.
4. **Storage Hardware Flaws**: If underlying storage hardware violates cache-flush commitments (`fdatasync`), write ordering cannot be guaranteed by software alone.
